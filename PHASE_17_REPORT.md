## 4. Job verification engine (17.4)

`jobagent/verify.py` — ten checks per job, six states, quality score:

1. HTTP availability (GET, not just HEAD) — 404/410 → expired; 4xx → blocked;
   5xx → degraded.
2. Redirect tracking (chain persisted; off-domain landing downgrades trust).
3. Application-page plausibility — content check for apply/job markers.
   **A bare HTTP 200 never yields `verified_open`** (tested explicitly).
4. Expiry detection — strong markers ("position has been filled", "no longer
   accepting", ...) beat nav-bar "apply now" links; past deadlines expire without
   fetching.
5. Duplicate detection — id + company/title dedup at ingest (existing, tested) +
   duplicate-submission guard at apply time.
6. Company-domain verification — registrable domain match vs company name and
   known ATS hosts.
7. Suspicious-domain detection — free-mail apply links, URL shorteners, raw IPs,
   punycode, typo-squats ("micros0ft" for Microsoft).
8. Salary consistency — min ≤ max, plausible LPA range, fresher-role sanity.
9. Freshness scoring (posted/discovered age).
10. Source reliability (from `data/source_stats.json` success rates).

States: `verified_open · probably_open · needs_manual · expired · suspicious ·
unavailable` (+ `unverified`). **Quality score 0-100** (availability 20 +
plausibility 20 + freshness 20 + domain trust 20 + salary 10 + reliability 10) is
stored separately from the candidate match score. First/last-verified timestamps,
method, final URL and redirect chain persist per job. SSRF guard: private/localhost
hosts are never fetched (tested). New jobs are verified during discovery; batch
re-check via `verify_batch()`; per-job via API/CLI. 16 dedicated tests.

- **The fill engine is preserved** (it was already semantic: `<label for>`,

- **New: session persistence + recovery** — every apply session checkpoints into
  the `apply_sessions` table (step, ATS, URL, tailored state) after each fill, so
  interrupted sessions can be inspected and resumed, and the queue knows what was

  upload, sensitive-field stops and CAPTCHA detection.

Hard rules preserved: never bypass CAPTCHA/MFA/login walls or bot protection;
never auto-click Naukri/Instahyre one-click applies; LinkedIn Easy Apply stops at

## 6. Application execution — three modes (17.6)

| Mode | What it does | Guards |
|---|---|---|
| **A — Discovery** | search → verify → eligibility → rank → shortlist | read-only |
| **B — Assisted** (default) | tailored resume + cover letter + grounded answers → visible browser → fill everything → **pause for human review** | fraud guard, never submits |
| **C — Authorized** | full submission on the user's behalf | see below |

**Mode C requires ALL of:**
1. `automation.authorized_submission: true` in config.yaml (default **false**, not
   a one-click UI switch);
2. explicit per-job approval (queue action `approve` → `awaiting_approval`);
3. every queue gate passing (limits, scores, eligibility, fraud flags,
   verification state, no prior submission, tailored resume exists);
4. no CAPTCHA/bot-protection on the page (detected → stop);
5. no login wall (password fields → stop; credentials are never entered);
6. no sensitive/legal fields left (Aadhaar, PAN, passports, consents, background
   checks, declarations, signatures, EEO demographics — 23 regex patterns);
7. no empty required fields.

The `submit-authorized` CLI worker then clicks Submit, waits, and records
**confirmation evidence**: screenshot + the platform's confirmation phrase +
final URL. **A job is marked `submitted` ONLY when a confirmation phrase is
found**; otherwise it goes to `needs_manual` with the reason, and no submission
row is written. Manual submissions ("Mark applied") record honest evidence too.
Never bypassed: CAPTCHA, MFA, authentication, bot protection, application
restrictions. No application fees are ever paid.

## 7. Smart application queue (17.7)

- **11 states:** new → analyzing → eligible → shortlisted → resume_prep → ready →
  awaiting_approval → applying → submitted | failed | needs_manual.
- **Per-opportunity columns** (all from persisted data): company, title, salary
  (CTC/stipend), location/remote, eligibility, match score, job quality,
  verification state, deadline (+urgency), resume readiness, queue state,
  pipeline status, gate verdict + reason.
- **Configurable limits** (`automation.*`): max/day (15), max/company (2), min
  match score (70), min eligibility (likely_eligible), min quality (40), min
  salary LPA (6), preferred locations. Mass low-quality applications are blocked
  by construction; relevance and deadline urgency drive prioritisation.
- **Actions:** analyze (verify+score+eligibility), shortlist, prepare (tailor
  resume + cover letter via the Resume Tailoring Agent), approve, apply
  (assisted/authorized). Every transition is a job event.
- **UI:** Queue page in the dashboard (all columns, state filters, action
  buttons, limits header). **CLI:** `python -m jobagent queue`.

## 9. Email & application monitoring (17.9)

`jobagent/email_sync.py` — optional, **read-only**:
- Transports: Gmail OAuth (read-only scope, user's own credentials, token in
  gitignored `data/`) or IMAP (any provider / Gmail app password).
- Classification: deterministic keyword rules first (high precision), Groq for
  uncertain messages; labels: confirmation, assessment, interview, rejection,
  offer, recruiter, other.
- Matching: incoming mail → existing applications by company tokens; status
  transitions (rejection/assessment/interview/offer) + notifications.
- Confidence < 0.6 or `other` → flagged for human review (`reviewed=0`).
- **Nothing is ever sent** — the module contains no send capability at all
  (asserted by test). Follow-up emails are drafts the user copies.
- Endpoints: `GET /api/emails`, `GET /api/emails/status`, `POST /api/emails/sync`,
  `POST /api/emails/{id}/review`.

## 11. Performance & reliability (17.11)

- **Concurrent ingestion** — simple API sources fetched in a thread pool
  (`search.ingest_concurrency`, default 4) with per-source error isolation; one
  dead source never kills a run (each source has try/except + health tracking).
- **Persistent task history** — `task_history` table + `GET /api/tasks`; the
  one-task-at-a-time rule is preserved (they share the browser + LLM budget).
- **Backups** — WAL-safe hot backup: `python -m jobagent backup` and
  `POST /api/backup` (SQLite backup API, no locks).
- **Health** — `GET /api/health` now reports llm backend + key presence, DB job
  count, sources degraded today, running task — degraded mode is explicit: the
  product keeps working if Groq or any single source is down (local prefit
  fallback + cached scores + per-source isolation, all pre-existing).
- **Politeness** — every fetcher rate-limits (0.3-3s delays), retries with
  backoff (httpx transport retries), robots.txt respected by design (adapters
  only use official APIs/public pages; blocked platforms are external links).

## 13. Known limitations

1. Platforms in §2's unsupported table cannot be legally/reliably ingested from
   this environment — external-link discovery only, with reasons. That is an
   honest boundary, not a bug; on a residential IP the same probes may differ.
2. LinkedIn guest search is rate-limited; Naukri needs a visible browser (captcha
   on datacenter IPs) — human-in-the-loop by design.
3. Gmail OAuth is mocked in tests; live sync needs the user's own Google
   credentials (README documents the one-time setup).
4. Authorized submission (Mode C) is deliberately conservative — it stops on
   anything unusual; several ATS flows (Workday SSO, Taleo sessions) will usually
   land in `needs_manual` rather than risk a bad submission. That is the intended
   trade-off.
5. Live feed counts vary daily (Himalayas/Jobicy yield is modest by nature).
6. Single-user, local-first product; multi-tenancy remains out of scope
   (documented since phase 14).
